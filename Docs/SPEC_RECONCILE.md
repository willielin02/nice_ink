# SPEC ↔ 實作 對帳清單

**這份文件存在的理由**：2026-08-29 使用者質問「我的 spec 為什麼和現狀有這麼大的落差？」
——SPEC 自 v4.0g（08-18）停了十一天，累積九項未回寫。**這不是疏忽，是制度不對稱**：
CLAUDE.md 鐵律「未經使用者明說不得動 SPEC」擋住了 Claude 編造設計（它有效），但**沒有
配對的另一半要求把使用者真正的定案回寫**，所以預設行為就是漂移——定案堆在對話與帳本裡
（SHIP_PLAN 已 3200+ 行），SPEC 安靜地變成歷史文件。而 SPEC 是「設計的唯一權威」，
**過期的權威比沒有權威更糟**：下一個 session 會照著它做。

所以這份清單的目的不是記錄那一次對帳，而是**讓下次是「重跑」而不是「從頭來」**。

---

## 怎麼用

1. 逐條跑「可查證斷言」表——每條都有明確的查法（grep 什麼、看哪個欄位）。
2. 對不上的，先分類再動手：
   - **SPEC 舊、實作對**（使用者後來另有定案）⇒ 更新 SPEC。
   - **實作漂了、沒有決定**⇒ **不要改 SPEC**，回報使用者。拿改 SPEC 來蓋掉實作漂移
     ＝把 bug 追認成設計。
   - **設計意圖類斷言**（「大膽在指認端安全、在創作端危險」之類）⇒ 標「無法自動查證」，
     不要為了讓表好看而硬給結論。
3. 跑完更新 SPEC 版本行的「與實作對賬日期」——**那個日期就是 SPEC 的保鮮期**。
4. 跑完更新本檔末尾的「上次對帳」。

使用者的定案，所以走「定案回寫」那條路，不走對帳。
